# Android-Go 交互优化方案

## 现状分析

当前数据流有两条路径：

**推送路径（Go → Android，1Hz）**：`metricsTick` 每秒通过 JNI 推送 7 个标量（peerCount, direct, relay, txSpeed, rxSpeed, totalTx, totalRx）到 `P2PTapVpnService.onMetricsUpdate`。

**拉取路径（Android → Go，按需）**：`P2PTap.getStatsJSON()` 返回完整 JSON 快照，经过 `StatsSnapshotParser.parse` 解析后写入 `P2PStateRepository`。

**核心问题**：推送路径只带 7 个标量，没有 peer 详情，导致 UI 必须通过拉取路径获取完整 JSON 才能显示 peer 列表。每次拉取都要拿全局 `mu` 锁、调 `UpdateWebCollectorState()`（重建所有 peer DTO）、`GetResponse()`、`json.Marshal`——而 `Stop()` 也在同一个 `mu` 下阻塞数秒。这就是为什么代码里有 `PULL_TIMEOUT_MS=5000`、`PULL_FAIL_STREAKS=3`、`STOP_TIMEOUT_MS=15000`、专门的 `statsPullExecutor` 线程。

## 改动内容

### Phase 1：Android 侧（不需要重编 AAR）

#### 1.1 修复 MainActivity 的 peer 计数分歧（bug fix）

`MainActivity.kt:95-97` 从 `snapshot.peers` 重新计算 `activeCount`，而推送路径的 `P2PStateRepository.metrics.value.peerCount` 已经是权威值（在 Go 的 `metricsTick` 里推导）。当前代码重新计算导致两个数字可能不同步。

**改动**：用 `viewModel.metrics.value.peerCount` 替代重算，与推送值保持一致。

**文件**：`mobile/src/main/java/app/fjj/p2ptap/MainActivity.kt`

#### 1.2 用 LogCollector 替换手机 LogViewerActivity 的 logcat 子进程

`LogViewerActivity.kt:168` 仍然 `Runtime.exec("logcat -v time -s ...")` 起子进程。TV 已经用 `LogCollector.tail()` 轮询。`LogCollector` 通过平台 log sink 在同一进程内捕获日志，不需要 shell 权限。

**改动**：把 `LogViewerActivity` 的 logcat 子进程替换为 `LogCollector.tail()` 轮询，与 TV 的 `TvLogsActivity` 走同一条路。删除 ANSI 正则和子进程管理代码。

**文件**：`mobile/src/main/java/app/fjj/p2ptap/ui/LogViewerActivity.kt`

#### 1.3 优化 LogBuffer.tail()

`LogBuffer.tail(maxLines)` 当前先调 `snapshot()`（复制全部 2000 条），再 `subList`。TV 的 `TvLogsActivity` 每 1500ms 调一次，每次都复制全量环形缓冲区。

**改动**：直接从尾部往前遍历，只复制最后 N 条。从 O(capacity) 降到 O(maxLines)。

**文件**：`core/src/main/java/app/fjj/p2ptap/service/LogBuffer.kt`

### Phase 2：Go 侧（需要重编 AAR）

#### 2.1 记忆化 UpdateWebCollectorState()

当前在 `metricsTick`（1Hz）和 `getStatsJSONLocked`（每次拉取）都调 `n.UpdateWebCollectorState()`。这个函数每次：重新解析所有 bootstrap/static peer multiaddr、调 `os.Hostname()`、重新安装 TAP self-test closure、重建所有 peer DTO。这些在一个 session 内大部分是静态的。

**改动**：加一个 dirty flag。在 `Start()` 时设为 true。在 `metricsTick` 里检测 peer 集合是否变化——变了才调 `UpdateWebCollectorState()`。这样从每秒调一次降到只在 peer 真正变化时调。

**文件**：`p2ptap-core/pkg/android/android.go`

#### 2.2 在 GetStatsJSON 中提前释放 mu

当前 `getStatsJSONLocked` 在全局 `mu` 下执行 `UpdateWebCollectorState()` + `GetResponse()` + `json.Marshal`。`Stop()` 也在同一个 `mu` 下执行多秒的 `n.Close()`。两个操作竞争同一个锁，导致 `PULL_TIMEOUT_MS=5000` 的超时存在。

**改动**：在 `mu` 下只做 `UpdateWebCollectorState()` + `GetResponse()`（快操作），释放 `mu` 后再 `json.Marshal`（慢操作，不依赖锁）。`Stop()` 可以在这期间完成。

```go
// 现在
func getStatsJSONLocked() string {
    mu.Lock()
    defer mu.Unlock()
    // ... UpdateWebCollectorState + GetResponse + json.Marshal 全在锁下
}

// 改后
func getStatsJSONLocked() string {
    mu.Lock()
    if instance != nil {
        instance.UpdateWebCollectorState()
    }
    var resp *web.StatsResponse
    if activeCollector != nil {
        resp = activeCollector.GetResponse()
    }
    mu.Unlock()
    // marshal 在锁外
    if resp != nil {
        data, err := json.Marshal(resp)
        if err == nil { return string(data) }
    }
    return "{}"
}
```

**文件**：`p2ptap-core/pkg/android/android.go`

## 不做的事

- **不改推送接口签名**（加 peer 详情到 `OnMetricsUpdate` 需要改 interface，gomobile 重新生成 Java 接口，影响面大，收益有限——拉取路径已经能获取 peer 数据）
- **不删 P2PTap struct wrapper**（`android.go:741-899` 的重复 API，是 gomobile 的导出模式，删了会破坏调用方）
- **不集中化手机轮询**（`MainActivity` 的 1500ms 循环 + 3 个 Dialog 的 `refreshStats()` 已经被 TTL=1200ms 保护，暂时够用；集中化会引入新的调度器，增加复杂度）
